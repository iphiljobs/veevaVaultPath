04 / PRACTICAL MILESTONES

Two small labs, grounded in the official model

LAB 01 · VQL

Extract parents and related children

Official-style parent-to-child relationship query. Replace object, field, relationship, and reference names with the exact API names configured in your Vault. Run with a test account that has appropriate read access.

SELECT id, name__v,
       (
         SELECT id, name__v,
                country__cr.id, country__cr.name__v
         FROM approved_countries__cr
       )
FROM product__v

Read the result shape: each Product appears at the top level, with its related approved-country records nested under approved_countries__cr. The country fields are read through the child record's country__cr relationship. This is an outer join: Products remain in results even when they have no related approved-country record. Check current VQL documentation for filtering related rows and response pagination.

LAB 02 · VAULT JAVA SDK

Reject an invalid record before save

Illustrative BEFORE_INSERT / BEFORE_UPDATE trigger: an exception-type training request requires a justification. The example handles every record change in the trigger context and attaches a record-level validation error.

package com.veeva.vault.custom.training;

import com.veeva.vault.sdk.api.core.ValueType;
import com.veeva.vault.sdk.api.data.Record;
import com.veeva.vault.sdk.api.data.RecordChange;
import com.veeva.vault.sdk.api.data.RecordEvent;
import com.veeva.vault.sdk.api.data.RecordTrigger;
import com.veeva.vault.sdk.api.data.RecordTriggerContext;
import com.veeva.vault.sdk.api.data.RecordTriggerInfo;

@RecordTriggerInfo(
    object = "training_request__c",
    events = {RecordEvent.BEFORE_INSERT, RecordEvent.BEFORE_UPDATE}
)
public class JustificationRequiredTrigger implements RecordTrigger {

    @Override
    public void execute(RecordTriggerContext context) {
        for (RecordChange change : context.getRecordChanges()) {
            Record proposed = change.getNew();
            String requestType = proposed.getValue(
                "request_type__c", ValueType.STRING
            );
            String justification = proposed.getValue(
                "justification__c", ValueType.STRING
            );

            boolean isException = requestType != null
                && "exception__c".equals(requestType);
            boolean hasJustification = justification != null
                && !justification.trim().isEmpty();

            if (isException && !hasJustification) {
                change.setError(
                    "JUSTIFICATION_REQUIRED",
                    "Provide a justification for exception requests."
                );
            }
        }
    }
}
Check before compiling

Confirm the SDK API signatures against the Java SDK documentation and Javadocs for the SDK version selected by your Vault release. Field API names and stored picklist values must match your schema.

Understand the lifecycle

BEFORE triggers can set an error on a record to prevent the operation. AFTER triggers run after the operation; use the documented exception behavior for the target SDK. Triggers execute in Vault’s server context and should be safe for bulk record changes.

Official references: VQL object outer joins · Record Trigger anatomy · RecordChange Javadocs. The Java block illustrates the trigger pattern; compile against the current SDK in the Vault SDK developer environment before adoption.
